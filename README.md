# ITMO.Queue Backend

Стартовый архитектурный каркас backend-сервиса для управления учебными сессиями и очередями на защиту лабораторных работ. Это **один репозиторий и модульный монолит**: модули разделены по доменам и имеют явные границы, но пока не разворачиваются как отдельные сервисы.

## Стек

- **Python + FastAPI** — REST API и серверная бизнес-логика.
- **TypeScript** — типизированные API-контракты в `packages/contracts-ts`; они должны соответствовать OpenAPI-схеме FastAPI. TypeScript-код не дублирует backend-бизнес-логику.
- **PostgreSQL** — основное долговременное хранилище и источник истины для пользователей, учебных сущностей, сессий, очередей, слотов, результатов и аудита.
- **Redis** — кэш, временные счётчики/данные и доставка сигналов между экземплярами. Не использовать как единственный источник критичного состояния очереди.
- **SQLAlchemy + Alembic** — слой доступа к PostgreSQL и миграции.
- **pytest** — тестирование.

Версии зависимостей и окончательный инструментарий следует согласовать с тимлидом до реализации.

## Архитектура в двух словах

- `src/itmo_queue/api/` — HTTP-слой: маршруты, схемы запросов/ответов и зависимости FastAPI.
- `src/itmo_queue/modules/` — доменные модули: `auth`, `academic`, `sessions`, `queues`, `realtime`, `notifications`, `integrations/itmoid`, `audit`.
- `src/itmo_queue/infrastructure/` — конкретные адаптеры PostgreSQL и Redis, реализации портов и внешние технические интеграции.
- `src/itmo_queue/workers/` — фоновые обработчики, в том числе доставка Outbox-событий и уведомлений.
- `packages/contracts-ts/` — TypeScript-контракты API. Скрипт `npm run generate` экспортирует OpenAPI из FastAPI и генерирует TS-типы.
- `migrations/` — версионируемые изменения схемы БД.
- `tests/` — unit-, integration- и API-тесты.

## Архитектурная схема

Откройте `ITMO.Queue.canvas` в Obsidian. Правила зависимостей и поток обработки изменений описаны в `ARCHITECTURE.md`.

## Основные правила

1. API-слой вызывает сценарии приложения, а не обращается к БД напрямую.
2. Доменная логика не зависит от FastAPI, SQLAlchemy или Redis.
3. Каждый модуль владеет своим доменом и портами. Другие модули используют только его публичный интерфейс, а не внутренние классы/таблицы.
4. PostgreSQL остаётся источником истины. Изменение бизнес-состояния и запись Outbox-события выполняются в одной транзакции.
5. Worker публикует события после фиксации транзакции; обработчики должны быть идемпотентными.
6. SSE уведомляет клиентов об изменениях, но после переподключения клиент должен уметь получить актуальное состояние через API.
7. Redis — ускоряющий/вспомогательный слой; для временных ключей должны быть определены TTL и стратегия восстановления.
8. Авторизация MVP по табельному номеру не должна делать его постоянным первичным ключом. Использовать внутренний UUID пользователя и отдельную связь с внешней identity для будущей интеграции ITMO.ID.

## Статус

Каркас и папки подготовлены для обсуждения. Это не законченная реализация приложения: бизнес-правила очередей, модель прав, подтверждение владения табельным номером, точная схема БД и версии зависимостей должны быть согласованы отдельно.
