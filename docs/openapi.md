# API ITMO.Queue

Swagger UI: `/docs`, JSON-контракт: `/openapi.json`, префикс: `/api/v1`.
Схемы запросов, ответов, UUID, перечисления и ошибки доступны в OpenAPI.
HTTP использует snake_case. В сообщениях WebSocket входные поля `queueId`,
`targetQueueNumber`, `requestId` сохраняют названия из документации фронтенда.
Идентификаторы везде — строки UUID; позиции и приоритеты — целые числа.

## Вход и права

`POST /auth/login` принимает `{"login":"m.kovzik","password":"..."}`.
Также можно войти по шестизначному ИСУ: сначала ищется точное совпадение логина,
затем ИСУ. Ответ — id, имя, логин и роль. HttpOnly cookie называется `sessionId`,
SameSite=Lax, Secure включён по умолчанию. Для локального HTTP задайте
`SESSION_COOKIE_SECURE=false`. Серверные сессии хранятся в Redis с TTL;
повторный вход меняет токен, выход удаляет его. Роль и активность проверяются в БД.
Пароли хешируются версионированным bcrypt(SHA-256); старые форматы читаются.

Фронтенд отправляет запросы с `credentials: "include"`. Разрешённые адреса задаются
в `CORS_ORIGINS` (JSON-массив точных origin). В production используйте общий origin
через reverse proxy и HTTPS. WebSocket проверяет Origin по тому же списку.

- Студент видит общедоступные сеансы и сеансы своего потока, свои записи и историю.
- Преподаватель управляет назначенными ему сеансами. Для создания нужны
  `can_create_queues=true` и назначение на дисциплину.
- Администратор создаёт пользователей и справочники, назначает права и имеет доступ ко всем сеансам.
- Пароли/хеши не возвращаются. Студенту не возвращаются чужие артефакты и история.

## Маршруты

Пути ниже указаны после `/api/v1`. Точные тела и типы ответов смотрите в Swagger.

| --- | --- |
| POST `/auth/login`, POST `/auth/logout` | Вход, выход (204) |
| POST `/auth/register` | Создать пользователя: name, login, isu, password, role, stream_id |
| GET `/me` (и старый `/auth/me`) | Профиль |
| GET `/users`, PATCH `/users/{user_id}` | Пользователи; активность, поток, can_create_queues, discipline_ids |
| GET/POST `/disciplines`, PATCH `/disciplines/{discipline_id}` | Справочник дисциплин |
| GET/POST `/streams` | Справочник потоков |
| GET/POST `/works`, PATCH `/works/{work_id}` | Работы, их порядок и активность |
| GET `/session-options` | Дисциплины, преподаватели с допусками и работы для формы |
| GET/POST `/queues`, GET/PATCH `/queues/{queue_id}` | Поиск, создание, просмотр и настройки сеанса |
| POST `/queues/{queue_id}/registration` | Открыть/закрыть запись: `{"open":true}` |
| POST `/queues/{queue_id}/activate` | Начать активную защиту |
| POST `/queues/{queue_id}/finish` | Завершить, `{"reason":"Занятие закончено"}` для оставшихся записей |
| GET `/me/queues`, GET `/students/{student_id}/queues` | Свои записи / записи студента (admin) |
| GET `/me/history`, GET `/students/{student_id}/history` | Своя история / чужая (admin) |
| GET `/queues/{queue_id}/history` | История сеанса для его преподавателей/admin |
| POST `/queues/{queue_id}/entries` | Записаться на список работ |
| PATCH `/queues/{queue_id}/entries/me` | Изменить свои работы и ссылки без изменения места |
| DELETE `/queues/{queue_id}/entries/me` | Отменить свою запись |
| POST `/queues/{queue_id}/entries/me/move-to-end` | Один самостоятельный перенос в конец |
| POST `/queues/{queue_id}/entries/me/switch/{queue_number}` | Предложить обмен с позицией >3 |
| GET/POST `/queues/{queue_id}/swaps` | Свои предложения / предложение по двум entry_id (query) |
| POST `/queues/{queue_id}/swaps/{swap_id}/accept`, `/decline`, `/cancel` | Принять, отклонить, отменить |
| POST `/queues/{queue_id}/call-next` | Вызвать следующего |
| PATCH `/queues/{queue_id}/students/{student_id}` | Вызвать, начать защиту или перенести преподавателем |

| DELETE `/queues/{queue_id}/students/{student_id}` | Удалить запись с причиной и запретом повторной записи |
| GET `/queues/{queue_id}/bans`, DELETE `/queues/{queue_id}/students/{student_id}/ban` | Посмотреть / снять запрет |
| GET `/me/notifications`, POST `/me/notifications/{notification_id}/read` | Уведомления и отметка прочтения |
| GET `/queues/{queue_id}/stream`, WS `/ws/me` | SSE и персональный realtime |

Старые методы действий по `/entries/{entry_id}` и CRUD `/groups`, `/students`
сохранены. CRUD пользователей/учебных групп доступен только администратору;
поток доступа к очереди задаётся через `/streams` и `stream_ids`.

## Основные контракты

Создание сеанса: `discipline_id`, `title`, `planned_start`, `planned_end`
(ISO 8601 с часовым поясом), `teacher_ids`, `works: [{work_id, priority}]`.
Дополнительно: `description`, `location`, `quota`, `avg_duration_min` (по умолчанию 10),
`stream_ids` (пусто = доступно всем студентам), `registration_open` (по умолчанию true).
Преподаватель-создатель автоматически назначается. Все принимающие должны быть
активны и иметь допуск к дисциплине. Приоритеты работ определяют их порядок.

Этапы: `preliminary`, `active`, `finished`. Поля `stage` и `registration_open`
меняются независимо; паузы в MVP нет. PATCH может активировать сеанс или завершить
его (`stage=finished`, `finish_reason`), обратные переходы запрещены. Завершение
невозможно при текущих вызовах/защитах; ожидающие записи и обмены отменяются.
Повторная активация/завершение безопасны. Плановое время не меняет этап автоматически.
Настройки завершённого сеанса не редактируются. Список работ нельзя менять после записи,
а преподавателя с текущей защитой нельзя исключить из сеанса.

Пример записи:

```json
{"works":[
  {"work_id":"11111111-1111-4111-8111-111111111111","artifact_url":"https://github.com/example/lab-3"},
  {"work_id":"22222222-2222-4222-8222-222222222222","artifact_url":"https://github.com/example/lab-4"}
]}
```

Ответ включает `works`, позицию, `is_top3`, `is_reserve`, `self_moves_count`,
текущего преподавателя/attempt_id. Старые `work_id`/`artifact_url` присутствуют
только для одной работы и помечены deprecated. Квота мягкая; `null` означает
отсутствие лимита. При уходе/удалении место основной группы получает первый резерв.
Топ-3 — первые три **ожидающие** записи; самостоятельные выход, перенос и обмен
для них запрещены, как и для вызванных/защищающихся. Преподаватель может переносить
ожидающих/вызванных с причиной. При переносе вызванного текущая попытка прекращается.
После удаления повторная запись запрещена до отдельного снятия запрета.

`PATCH .../students/{student_id}`: `status=called` вызывает участника;
для нарушения порядка нужно `confirm_out_of_order=true`. `status=in_defense`
требует `attempt_id`; `status=waiting` переносит в конец и требует `reason`.
На одного преподавателя и студента допустима одна текущая попытка, в том числе
при работе в разных сеансах. Два преподавателя получают разных участников.
Для повторов `call-next` и PATCH участника используйте один `Idempotency-Key`
на одно действие; новый ключ нужен для следующего самостоятельного действия.

Оценивание требует `attempt_id`, `status=accepted`, `results`:
`[{"work_id":"...","kind":"score","score":7.5}]` либо `kind=accepted` без score.
Результаты фиксируются только для переданных работ этой записи. Нерассмотренная работа
не получает результат автоматически. Начало защиты обязательно перед оцениванием.
`status=absent` без results допустим только до начала защиты: попытка получает
`no_show`, запись уходит в конец, преподаватель освобождается. Повтор того же запроса
не создаёт новую неявку/оценку и не переносит снова. Завершённые результаты неизменяемы.

GET `/queues` поддерживает `search` (дисциплина, название, преподаватель), `discipline`,
`stage`, `registration_open`, `stream`, `limit` (1–100), `offset`.
GET истории: `date` (дата UTC), `discipline`, `work`, `limit`, `offset`.
Ответы списков очередей и истории — массивы. История сохраняет отдельные попытки
и дробные баллы; доступ преподавателя ограничен его сеансом.
В деталях очереди есть `my_entry`, список участников и преподавателей, `wait_status`
и приблизительное `estimated_wait_minutes`. Прогноз рассчитывается только для
активного сеанса с одним принимающим: отсчёт идёт от начала защиты. Для вызова
без начала, затянувшейся защиты и предварительной записи возвращается отдельный
статус вместо неверного численного обещания.

## SSE и WebSocket

SSE сразу отправляет `snapshot` с актуальными деталями. Затем отправляются
`queue.updated`, `participant.status_changed`, `queue.status_changed` с `id`
и публичным списком students. При изменении настроек фронтенд перечитывает детали
очереди. Для восстановления передайте `Last-Event-ID` (или `after`), heartbeat —
каждые 15 секунд. События и уведомления хранятся в PostgreSQL и доступны между
процессами; опрос раз в секунду. Cookie/допуск перепроверяются; `auth.required`
означает, что нужно закрыть поток и заново войти/получить доступ.

WebSocket использует ту же cookie. Вход:

```json
{"type":"switch.propose","queueId":"UUID","targetQueueNumber":5}
{"type":"switch.accept","requestId":"UUID"}
{"type":"switch.reject","requestId":"UUID"}
{"type":"switch.cancel","requestId":"UUID"}
```

Выход: `switch.ack`, `switch.incoming`, `switch.resolved`, `error` (status/detail),
а также сохранённые персональные уведомления. Поле `request` содержит SwapRead
из OpenAPI, `notificationId` позволяет убрать повторы после переподключения.
Предложение действует 45 секунд; expires_at возвращается явно. Истечение
обрабатывается каналом и при чтении/действии; просроченный обмен никогда не применяется.
Обе записи должны ждать вне топ-3. Подтверждение повторно проверяет условия под
блокировкой очереди. Сначала фиксируется изменение в БД, затем доступно событие.
Повтор принятия возвращает сохранённый результат; устаревшее предложение получает
cancelled/expired. После отключения состояние восстанавливается через GET очереди,
GET swaps и GET notifications. Сервер не гарантирует прочтение уведомлений офлайн.

## Ошибки и источники

Формат ошибки: `{"detail":"..."}`; для валидации detail — массив ошибок FastAPI.
401 — нет/истекла сессия, 403 — нет прав/допуска или запрещено самостоятельное
действие, 404 — объект не найден, 409 — конфликт состояния/дубликат,
422 — неверные поля/ссылки на сущности. Старые методы записи/переноса используют
также 400 для закрытой записи, недопустимой работы и повторного самостоятельного переноса.

Основа: [сценарии MVP](https://github.com/ITMO-QUEUE/itmo-queue-docs/blob/main/docs/analysis/user-scenarios.md)
и [предложение API фронтенда](https://github.com/ITMO-QUEUE/itmo-queue-docs/blob/api/docs/api/API_DOCUMENTATION.md).
При расхождениях приняты правила MVP: три этапа без Paused, оба участника вне топ-3,
UUID вместо числовых примеров, запись на несколько работ. Актуальный контракт
для генерации типов фронтенда — `/openapi.json`.
