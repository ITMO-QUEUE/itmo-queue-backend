## Повторение HTTP smoke

Запускать на отдельной тестовой БД: каждый прогон создаёт уникальные тестовые
аккаунты, дисциплину, работы и сеанс. Скрипт не удаляет существующие данные,
не меняет существующих пользователей и не печатает пароли в журнал.

1. Скопировать `.env.example` в `.env`, задать локальный пароль PostgreSQL.
2. Установить backend: `python -m pip install -e ".[dev]"`.
3. Запустить сервисы: `docker compose up -d --wait postgres redis`.
4. Применить миграции: `python -m alembic upgrade head`.
5. На новой БД один раз выполнить `python -m itmo_queue.bootstrap`.
6. Запустить API: `python -m uvicorn itmo_queue.main:app --host 127.0.0.1 --port 8000`.
7. В другом терминале выполнить:

```sh
python -m itmo_queue.smoke --base-url http://localhost:8000 --origin http://localhost:5173
```

Скрипт интерактивно спросит логин и пароль существующего администратора. Для
автоматизации доступны `SMOKE_ADMIN_LOGIN` / `SMOKE_ADMIN_PASSWORD`; не хранить
их в репозитории. Профиль администратора, пароли и cookie в отчёт не выводятся.

Сценарий: создать аккаунты через API → назначить дисциплину → войти преподавателем
→ создать сеанс с новыми работами/потоком → дать доступ студенту → записаться
на две работы с артефактами → проверить перезагрузку и повтор записи → активировать
→ вызвать → повторить вызов с тем же Idempotency-Key → начать защиту → сохранить
отдельные результаты → повторить оценивание → прочитать историю через новую
HTTP-сессию с прежней cookie → завершить → выйти и получить 401.

Успех — JSON с queue_id, entry_id, attempt_id и пройденными checks, код выхода 0.
При неверном статусе, CORS или отсутствии HttpOnly cookie скрипт завершится ошибкой.

## Подготовка данных для браузера

Чтобы оставить незавершённый сеанс и аккаунты для команды:

```sh
python -m itmo_queue.smoke --prepare-only --origin http://localhost:5173 --credentials-file .smoke/ui-accounts.json
```

Файл содержит приватные пароли только созданных demo-аккаунтов, UUID сеанса и работ.
Каталог `.smoke/` исключён из Git; файл не перезаписывается. Для повторного запуска
выбрать новое имя файла. Использовать логины/пароли из accounts.student и
accounts.teacher для ручного входа в настоящий frontend.

Frontend запустить из его репозитория: установить зависимости `pnpm install --frozen-lockfile`,
скопировать `.env.example` в `.env.dev`, задать `VITE_API_URI=http://localhost:8000`.
Команда `pnpm dev --host 127.0.0.1 --port 5173 --strictPort`; открыть
`http://localhost:5173/auth`. Использовать одинаковое имя хоста (localhost) для
frontend и API. В backend нужны `SESSION_COOKIE_SECURE=false` и
`CORS_ORIGINS=["http://localhost:5173"]`. Для HTTPS Secure остаётся включённым.

После готовности экранов повторить: создание сеанса преподавателем → поиск и
запись студента с двумя ссылками → вызов и защита → отдельные результаты → история
студента. Проверить это после перезагрузки страницы. Никаких моков, SQL-подготовки
или ручной замены cookie в этом сценарии быть не должно.

## Автоматические проверки

`tests/test_smoke.py` использует тот же модуль, настоящий Uvicorn, PostgreSQL и Redis,
свежие аккаунты и Origin другого порта. Запускается обычным `python -m pytest` в CI.
Регрессионные тесты прав, конкуренции, выбранного студента и переходов сеансов:
`tests/test_sessions.py`, `tests/test_full_api.py`. В CI сначала применяются миграции,
затем Ruff/pytest и `alembic check`.
