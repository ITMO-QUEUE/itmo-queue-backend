# Архитектура и правила зависимостей

## Направление вызовов

```text
External clients
    -> API (FastAPI / DTO / validation)
    -> Application use cases of a domain module
    -> module ports (repositories, event publisher, providers)
    <- infrastructure adapters implement those ports
          -> PostgreSQL / Redis / external systems

PostgreSQL transaction: business state change + Outbox row
    -> background worker reads Outbox
    -> event publisher / Redis fan-out
    -> Realtime module streams updates to clients through SSE
```

## Границы папок

| Папка | Владеет | Может зависеть от | Не должна делать |
|---|---|---|---|
| `api/` | HTTP routes, DTO, validation, DI | публичные application-интерфейсы модулей, `core/` | SQL-запросы и бизнес-правила |
| `modules/<module>/domain/` | сущности, value objects, правила домена | стандартная библиотека и другие типы домена по явному контракту | импортировать FastAPI, SQLAlchemy, Redis |
| `modules/<module>/application/` | сценарии/use cases | свой `domain/`, свои `ports/`, публичные контракты других модулей | обращаться к инфраструктуре напрямую |
| `modules/<module>/ports/` | абстракции хранилищ и внешних зависимостей | типы домена модуля | содержать реализацию SQL/Redis |
| `infrastructure/` | реализации портов и технические адаптеры | порты модулей, драйверы БД/Redis | становиться местом бизнес-правил |
| `workers/` | фоновые процессы и расписание задач | application-интерфейсы, инфраструктурные адаптеры | обходить use cases ради изменения домена |
| `packages/contracts-ts/` | типы API для TS-потребителей | опубликованная OpenAPI-схема | содержать вторую реализацию бизнес-логики |
| `tests/` | проверка поведения и интеграций | публичные интерфейсы и test fixtures | связывать production-модули друг с другом обходным путём |

## Межмодульные зависимости

- `queues` может использовать публичные интерфейсы `sessions` и `academic` для проверки права записаться в очередь и контекста лабораторной работы.
- `auth` предоставляет контекст пользователя и проверки доступа; не должен владеть логикой очередей.
- `realtime` подписывается на опубликованные события и не изменяет состояние очереди самостоятельно.
- `notifications` обрабатывает запросы/события уведомлений; доменные модули не импортируют её внутреннюю реализацию.
- `integrations/itmoid` изолирует протоколы ITMO.ID и маппинг identity; доменные модули не вызывают ITMO.ID напрямую.
- `audit` получает записи о значимых действиях через интерфейс/события и не становится владельцем чужих доменных таблиц.

Запрещены циклические импорты между модулями. Если два модуля начинают ссылаться друг на друга, пересмотреть контракт или вынести взаимодействие в application-level orchestration/event.

## Надёжность данных и событий

1. Сначала выполняется авторизация и доменная валидация.
2. Бизнес-состояние сохраняется в PostgreSQL в транзакции.
3. Outbox-событие записывается в той же транзакции.
4. Worker доставляет событие с retry и идемпотентностью.
5. Redis используется для ускорения/рассылки, а не как единственная долговременная запись.
6. SSE доставляет обновления подписанным клиентам; API остаётся способом восстановить полный актуальный state.

## Очереди

Поддерживаются два режима — живая очередь и временные слоты. До реализации нужно формально описать состояния и допустимые переходы, конкуренцию за слот, идемпотентность повторных команд, отмену/пропуск и запись результата защиты. Эти правила не зашиты в текущий скелет.

## Авторизация и ITMO.ID

Внутренний `user_id` — UUID. Табельный номер является атрибутом/связью идентичности, а не постоянным primary key. MVP должен предусматривать надёжную проверку владения учётной записью; простого ввода табельного номера без проверки недостаточно. Будущий ITMO.ID подключается через отдельный provider/adapter.
